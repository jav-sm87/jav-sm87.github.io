Caso de estudio

Alke Wallet: del prototipo al sistema real

El mismo producto, construido tres veces a lo largo del bootcamp. Cada versión resolvió un límite de la anterior.

  1. FrontendHTML, Bootstrap y jQuery. Un solo usuario fijo y el saldo guardado en el navegador.
  2. Base de datosMySQL con tres tablas, claves foráneas, restricciones CHECK y transacciones con COMMIT y ROLLBACK.
  3. Aplicación DjangoMultiusuario, con registro, sesiones, CRUD de cuentas, movimientos atómicos y pruebas automatizadas.

La actividad

En el módulo de Django había que construir la billetera como una aplicación web completa en Django: modelos con relaciones uno a uno, muchos a uno y muchos a muchos; operaciones CRUD; autenticación; panel de administración; consultas personalizadas y pruebas.

El desafío principal

Una billetera maneja dinero, y ahí no se acepta un error a medias. El reto tenía tres partes:

  • Consistencia: en una transferencia se descuenta de una cuenta y se suma a otra. Si el segundo paso falla, el primero no puede quedar aplicado.
  • Reglas de negocio: nadie puede retirar ni transferir más de lo que tiene, y ningún saldo puede quedar negativo.
  • Privacidad: un usuario conectado no debe poder ver la cuenta de otro, ni siquiera escribiendo su dirección a mano.

La solución

Cada operación pasa por tres filtros antes de tocar la base de datos.

El primer filtro es un mixin que exige sesión iniciada y busca la cuenta solo entre las del cliente conectado. El segundo compara el monto con el saldo. El tercero guarda la transacción y actualiza los saldos dentro de transaction.atomic(): si algo falla, Django deshace todo.

# gestion/views.py: el bloque atómico de una transferencia
if tipo in (Transaccion.RETIRO, Transaccion.TRANSFERENCIA) and monto > cuenta.saldo:
    form.add_error('monto', 'Saldo insuficiente para realizar esta operacion.')
    return self.form_invalid(form)

with transaction.atomic():
    form.instance.cuenta = cuenta
    response = super().form_valid(form)
    ...
    cuenta.saldo = Decimal(cuenta.saldo) - monto
    destino.saldo = Decimal(destino.saldo) + monto
    destino.save()
    cuenta.save()

Además, los modelos tienen validadores propios: el saldo no puede ser negativo y el monto mínimo de un movimiento es $0,01. Los montos usan DecimalField y no números de punto flotante, para evitar errores de redondeo con dinero.

Aprendizajes

  • En la versión de MySQL aprendí que un ROLLBACK manual puede fallar si se ejecutan sentencias sueltas que hacen COMMIT implícito. Por eso en Django la consistencia quedó en el código, con un bloque atómico, y no en pasos manuales.
  • La seguridad no se agrega al final: filtrar cada consulta por el usuario conectado desde el diseño evita que se filtren datos.
  • Escribir las pruebas me obligó a definir con precisión qué debe pasar en cada caso, y me dio confianza para cambiar el código sin romperlo.
